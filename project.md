# Placement Lab Project Guide

## Overview

Placement Lab is a Streamlit application for campus recruitment preparation. It combines three workflows in one interface:

1. A placement prediction form powered by two saved machine-learning models.
2. Randomized DSA and Aptitude assessments with answer explanations and topic-level results.
3. A 30-day practice plan that allocates more study time to weaker assessment results.

The top navigation switches between Prediction, Assessment, and 30-day plan. Assessment results and form state are kept in the current Streamlit session; they are not saved to a database or retained after the session ends.

### `app.py`

The Streamlit presentation layer and application controller. It sets page configuration and visual styling, renders the top navigation, collects prediction inputs, displays model results, runs quizzes, stores assessment results in session state, and renders the 30-day plan.

### `assessment.py`

The assessment and study-plan backend. It defines the DSA and Aptitude question banks, creates randomized attempts, scores selected questions, calculates topic-level scores, and builds the 30-day schedule.

### `predictor.py`

The machine-learning inference backend. It locates and caches the model artifacts, builds the model input row in the required feature order, and returns a prediction label and probabilities.

### `requirements.txt`

Python package requirements. `scikit-learn` is pinned to 1.6.1 because that is the version used to serialize these model artifacts. The manifest also installs Streamlit, pandas, and joblib.

### Model artifacts

- `campus_recruitment_gb_model.pkl`: Gradient Boosting model artifact.
- `campus_recruitment_tuned_rf_model.pkl`: Tuned Random Forest model artifact.

`predictor.py` expects both files at the project root. They are loaded using `joblib.load`; only load artifacts from a trusted source because pickle-based model formats can execute code while loading.

### `dataset/` and `models/`

These folders currently contain no files and are not used by the running application. The trained model artifacts are at the root. The application does not currently load a training dataset or retrain models.

### `.venv/` and `__pycache__/`

`.venv/` contains the local Python environment and installed dependencies. `__pycache__/` contains generated bytecode. Neither is application source; do not rely on either being present in a fresh checkout.

## Application Flow

### Navigation and page rendering

At startup, `app.py` configures the wide Streamlit page and injects CSS for the graphite, teal, and coral theme. The horizontal `Workspace` radio control is visually styled as a top tab bar. A `label_visibility="collapsed"` setting hides the control's default label while preserving its accessible name. The sidebar is hidden with CSS because navigation is in the main page header.

The selected `active_view` dispatches to one of three functions:

- `render_prediction()` renders profile inputs and invokes `predictor.predict()`.
- `render_assessment()` renders the subject selector, randomized quiz, score, topic signals, and answer review.
- `render_plan()` reads stored assessment scores and displays the generated plan in week tabs.

`page_header(kicker, title, description)` is shared page-header UI. It renders a small section label, page title, supporting text, and divider.

### Prediction workflow

1. The student enters academic, aptitude, experience, and placement-preparation values in the `student_profile` form.
2. On submission, the values are stored under `st.session_state["submitted_profile"]`.
3. The `Prediction view` selector chooses either both models or one model.
4. Each selected model is called with the same profile. Results display the predicted class, probability of placement, and confidence in the selected class.
5. If the two class predictions differ, the app flags the result as uncertain. The probability is an estimate from the trained model, not a placement guarantee.

Prediction inputs are currently held in session state. The app does not save student profiles to persistent storage.

## Prediction Backend Details

### Model loading

`predictor.py` defines:

- `PROJECT_ROOT`: the directory containing `predictor.py`.
- `MODEL_PATHS`: labels mapped to the two root-level `.pkl` files.
- `MODEL_NAMES`: the labels used by the UI model selector.
- `load_model(model_name)`: validates the requested name and file, loads the artifact with `joblib`, and caches the loaded model with `lru_cache`.

After loading, `load_model` compares the model's `feature_names_in_` to `FEATURE_COLUMNS`. This catches a missing, reordered, or otherwise incompatible feature schema before inference.

### Input feature contract

`FEATURE_COLUMNS` is the authoritative column order expected by both trained models:

1. `CGPA`
2. `HSC_Marks`
3. `Workshops/Certifications`
4. `Internships`
5. `Projects`
6. `SoftSkillsRating`
7. `PlacementTraining_Yes`
8. `SSC_Marks`
9. `ExtracurricularActivities_Yes`
10. `AptitudeTestScore`

`build_feature_frame(profile)` translates the human-readable UI values into a one-row pandas DataFrame using this exact order. The two Yes/No fields are encoded as integer flags: 1 for `Yes`, 0 otherwise.

`predict(model_name, profile)` calls `predict()` and `predict_proba()` on the selected estimator. Class `1` is treated as placed and class `0` as not placed. The returned `Prediction` dataclass contains:

- `label`: `Placed` or `Not placed`.
- `placement_probability`: the probability associated with class `1`.
- `confidence`: the largest probability returned for any class.

## Assessment Backend Details

### Question bank

`QUIZZES` is a mapping with two subjects: `DSA` and `Aptitude`. Each subject currently has 20 original `Question` records. A question stores:

- `prompt`: the question text.
- `options`: the four answer choices in their canonical bank order.
- `answer_index`: the zero-based index of the correct answer in `options`.
- `topic`: the skill category used for topic-level reporting and planning.
- `explanation`: the short explanation shown in answer review.

`QUESTIONS_PER_ASSESSMENT` is 8, so the app draws eight items from each 20-question subject bank per attempt.

### Creating a randomized attempt

`create_attempt(subject, excluded_question_indices=())`:

1. Checks that the requested subject exists.
2. Builds an eligible set excluding the previous attempt's question indices.
3. Uses `random.sample` to choose eight different questions without replacement.
4. Independently shuffles the four option indices for every selected question.
5. Returns a list of records containing each `question_index` and its `option_order`.

On the first visit to a subject, `render_assessment()` creates and stores an attempt in `st.session_state["quiz_attempts"]`. On retake, `start_new_attempt(subject)` excludes the previous attempt, creates another randomized set, clears that subject's old result, and increments its quiz version. The version is included in widget keys so old radio selections do not carry into the new attempt.

The no-repeat guarantee applies to the immediately previous attempt for that subject. Since each bank has 20 items and each attempt uses 8, there are enough remaining questions to avoid overlap on a retake. A later attempt may reuse questions from attempts older than the immediately previous one.

### Submitting and scoring

`render_assessment()` presents each selected question with its shuffled choices. When a student submits:

1. The app requires an answer to every question.
2. It translates each displayed choice back to the original answer index using the attempt's `option_order`.
3. It passes the selected bank indices and answers to `score_assessment()`.

`score_assessment(subject, answers, question_indices)` uses the sampled question indices to retrieve the correct question records. It calculates the total score and groups correct/total counts by topic. The result also includes a per-question review with the submitted answer, correct answer, correctness flag, and explanation.

The result is stored in `st.session_state["assessment_results"]` by subject. The results are used by the 30-day plan and the navigation-bar completion count.

## 30-Day Plan Logic

`build_30_day_plan(assessments)` returns 30 daily task records. Each record contains the day, phase, subject, topic focus, task description, and estimated minutes.

For each assessed subject, the planner uses the overall score and topic percentages. Topics are ordered from lowest score to highest, so the weakest topics are selected first and cycled through the subject's practice days. An unassessed subject is given a neutral 50% baseline and a balanced topic sequence.

For days 1-27, subject allocation is weighted by `max(10, 100 - score)`. Lower scores therefore receive a larger share of study days, while the minimum weight ensures stronger subjects still receive practice. The daily activity phase changes over the month:

- Days 1-7: build foundations, 25 minutes per day.
- Days 8-14: guided practice, 35 minutes per day.
- Days 15-21: timed problem sets, 40 minutes per day.
- Days 22-27: mixed revision, 45 minutes per day.
- Day 28: full-length mixed mock, 60 minutes.
- Day 29: error analysis, 35 minutes.
- Day 30: final simulation, 60 minutes.

`render_plan()` shows the baseline average, priority subject, and assessment coverage. It groups the schedule into four tabs and places each day's topic and instructions in an expander. If only one subject has been assessed, the UI explains that the missing subject follows a balanced foundation sequence until its diagnostic is completed.

## Streamlit Session State

The app uses the following keys:

| Key | Purpose |
| --- | --- |
| `active_view` | Currently selected top navigation view. |
| `submitted_profile` | Latest student profile submitted to the prediction form. |
| `assessment_results` | Latest scored result for each completed subject. |
| `quiz_attempts` | Current randomized questions and option orders for each subject. |
| `quiz_versions` | Per-subject counter used to create fresh quiz widget keys after a retake. |
| `quiz_subject` | Subject selected on the Assessment page. |

Streamlit session state is temporary. Closing the browser session or starting a new session clears profile, attempt, and assessment data.

## Setup and Run

From the project root on Windows:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m streamlit run app.py
```

Streamlit prints the local URL when the server starts. If the default port is already in use, use the URL and port shown by that process.

## Important Implementation Notes

- Keep `FEATURE_COLUMNS` synchronized with the feature names and order used when training both models. A schema mismatch is intentionally rejected by `load_model()`.
- Install dependencies from `requirements.txt` before loading the artifacts. In particular, keep scikit-learn at 1.6.1 unless the models are deliberately re-exported and verified for another version.
- When adding questions, use a unique prompt, a valid zero-based answer index, a useful topic name, and a concise explanation. Banks should contain at least `QUESTIONS_PER_ASSESSMENT` questions.
- Question state and results currently exist only in the active Streamlit session. Persistent accounts, saved history, or cross-device use would require a storage layer, which this project does not currently have.
- The current `dataset/` and `models/` directories are placeholders. If model training is added later, training data and model artifacts should be placed in documented locations and the corresponding paths updated in `predictor.py`.
